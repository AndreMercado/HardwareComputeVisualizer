I. Introduction

1. Purpose

This document specifies the requirements for the Hardware Compute Visualizer, a desktop application that gives the user a live, visual, truthful picture of what their PC hardware (CPU, GPU, and RAM, and later motherboard/chipset and storage) is doing while it executes real workloads. It is intended for both the users and the developers of the system.

2. Scope

The system shall:

  • Display a visual diagram of the PC's hardware components as selectable parts.
  • Allow the user to pick a target machine — the local PC, or a cloud machine the user rents, reached over SSH — then a component and a workload (2D or 3D) to run against it.
  • Execute the selected workload for real on the selected hardware — never a simulated or scripted result.
  • Poll live hardware telemetry and animate the diagram in real time based on that telemetry.
  • Display live stats for the running workload: utilization, memory bandwidth, and temperature at minimum; frame time for 3D workloads; power draw and FLOPS where the hardware and workload make them available.
  • Provide an "AI Benchmark Mode" in which a locally run AI agent performs an open-ended task and the user observes real, unscripted hardware behavior.
Out of scope: driver or firmware modification, overclocking, changing power states, clock speeds, or fan curves, any network dependency when testing the local PC, and renting, starting, stopping, or paying for cloud machines (the user manages these through their provider). A fixed AI/ML workload as a third test type is a stretch goal (VI.2), not part of the MVP.

3. Intended Audience

This document is intended for the developers building the application and for anyone evaluating what the finished product does. Developers should read Parts III and IV closely; evaluators can rely on Part II for a summary of what the app does.

II. Overall Description

1. Product Perspective

The Hardware Compute Visualizer is a standalone desktop application (built in Python with Tkinter) that combines a visual hardware diagram, a real-time telemetry pipeline, and a benchmark runner. A normal system monitor only reports a changing number; this application ties that number to a visible part of the PC shown doing the work. Tests can run on the local PC or on a cloud machine the user rents, so the app can also show hardware the user does not own.

2. Product Functions

  • Connect to a target machine — the local PC by default, or a rented cloud machine over SSH — and detect its CPU, GPU, and RAM.
  • Render a diagram of the PC with CPU, GPU, and RAM (MVP) as selectable, distinctly colored parts.
  • Let the user select a component by clicking it in the diagram or through its search box.
  • Let the user pick a 2D or 3D workload, or AI Benchmark Mode, for the selected component.
  • Run that workload for real on the actual hardware, and let the user stop it at any time.
  • Poll telemetry for the active component(s), including components they depend on (e.g., RAM feeding the GPU), at 10 Hz or greater with under 200 ms latency.
  • Animate the diagram (brightness/motion) at 60 FPS, driven by that live telemetry.
  • Display a live stat readout appropriate to the running test and a summary when the test ends.
  • Abort any test automatically if a component exceeds a safe temperature.

3. User Characteristics

The intended user is a PC enthusiast, hobbyist builder, or student who wants to see what their hardware is doing under load. Basic familiarity with PC components and desktop applications is expected; systems-programming or benchmarking expertise is not required.

5. Design and Implementation Constraints

  • Telemetry access is strictly read-only. The application shall never modify driver settings, clock speeds, fan curves, or power states.
  • When testing the local PC, the core benchmark/visual loop, including AI Benchmark Mode, shall function with no network connection. Remote mode needs a network connection only between the app and the cloud machine.
  • Diagram animation shall sustain 60 FPS during an active test.
  • Telemetry for MVP components shall be polled at 10 Hz or greater with under 200 ms latency on the local PC, and under 500 ms on a cloud machine to allow for network delay.
  • Telemetry polling and workloads shall run off the UI thread so they cannot stall rendering.
  • Tkinter's Canvas is not designed for 60 FPS animation. If profiling shows it cannot hold 60 FPS, the diagram renderer may move to a faster toolkit (e.g., pygame or PySide6) without changing these requirements.

6. Assumptions and Dependencies

  • The OS and vendor libraries expose utilization and memory counters for the installed hardware without kernel drivers.
  • NVIDIA telemetry depends on an installed NVIDIA driver that ships NVML.
  • AI Benchmark Mode depends on Ollama with the Llama 3.2 3B model installed locally. The model is downloaded once during setup; no network connection is needed after that.
  • Cloud machines are assumed to run Linux (Ubuntu 22.04 or later) with Python 3.11+ and the NVIDIA driver installed, and to allow SSH key login. Because they are virtual machines, CPU temperature and power are usually hidden and will show "unavailable". The user creates, starts, stops, and pays for the cloud machine through their provider (e.g., RunPod, AWS EC2, Lambda Labs).
  • The 3D workload depends on a working OpenGL 3.3 driver; on a headless cloud machine it renders off-screen through EGL.
  • The user does not run other heavy workloads during a test; the app reports what the hardware is doing, which includes other programs' load.

III. Functional Requirements

1. Summary & Use Case Diagram

The user picks a hardware part, picks a workload, and watches a real-time, truthful visualization of that hardware doing the work. Two actors drive the app: the User (selecting parts, starting and stopping tests) and the AI Agent (acting inside AI Benchmark Mode once the user starts it).

Tools used:

  • Python as the primary implementation language.
  • Tkinter for the user interface.
  • Paramiko (SSH) for connecting to rented cloud machines.
  • psutil for CPU and RAM utilization and memory usage.
  • pynvml (NVML) for NVIDIA GPU utilization, VRAM, temperature, and power.
  • LibreHardwareMonitor (optional, requires administrator) for CPU temperature and power.
  • Real, runnable 2D/3D workloads written for this project, which also report their own frame time, FLOPS, and bytes moved.
  • Ollama running Llama 3.2 3B (4-bit quantized, about 2 GB) as the AI agent's local model.

2. System Architecture

When the user starts a test, the UI layer sends start(test, part) to the Benchmark Runner and start(parts) to the Telemetry Poller, telling it which component(s) to watch. The runner executes the workload on the real hardware. On a cloud machine, the runner and poller run inside a small remote agent on that machine and send results back over SSH. The poller reads sensors at 10 Hz or greater (read-only) and passes cleaned values to the Diagram Renderer / Stat Readout, which draws at 60 FPS. When the test stops or completes, the runner reports completion and the poller stops.

5. Component Selection

UC-1Detect Hardware at Startup (Essential)

TriggerApplication launches, or the user changes the target machine (UC-2)
PreconditionNone
Basic Path
  1. The application queries the target machine's OS and vendor libraries for its CPU, GPU(s), and RAM — directly on the local PC, or through the remote agent on a cloud machine.
  2. Detected device names populate each part's search options.
  3. The diagram renders each detected part as selectable.
  4. Any part that cannot be detected is shown greyed out as "not detected".
Alternate Path
  1. No GPU is detected: the GPU part is greyed out as "not detected" and the 3D workload is disabled.
  2. NVML is missing: the GPU name is taken from the operating system and its GPU metrics show "unavailable".
PostconditionEvery detected part is shown as selectable and its search box lists the real device name.
RequirementFR-1: The application shall list only hardware actually detected on the machine. If more than one GPU is present, each shall be selectable separately.

UC-2Connect to a Remote Machine (Essential)

TriggerUser chooses "Remote machine" as the target and enters the host address, username, and SSH key file
PreconditionThe user has rented and started a cloud machine that accepts SSH key login
Basic Path
  1. User selects "Remote machine" and enters the host, username, and key file.
  2. The application connects over SSH using the key.
  3. The application checks that Python and the NVIDIA driver are present, copies the remote agent into a working folder, and starts it.
  4. The remote agent reports the machine's hardware (UC-1).
  5. The diagram shows the remote hardware, and the status line reads "Connected: HOST".
Alternate Path
  1. Login fails: an error explains why, and the target stays on the local PC.
  2. Python or the NVIDIA driver is missing: an error lists what is missing, and the target stays on the local PC.
  3. The connection drops during a test: all remote metrics show "unavailable" (UC-12), and the remote agent stops the workload on its own after 10 seconds without contact.
  4. The user switches back to the local PC: any remote test is stopped (UC-8), and the remote agent is stopped and removed.
PostconditionThe diagram shows the remote machine's hardware, and tests run on that machine.
RequirementFR-20: Remote connections shall use SSH with key authentication only; the application shall never store passwords or cloud-account credentials. FR-21: The application shall never create, start, stop, or resize cloud machines; the user manages them, and their cost, through the provider. FR-22: The remote agent shall stop any running workload if it loses contact with the application for 10 seconds. FR-23: The remote agent shall be read-only toward hardware settings, exactly as on the local PC, and shall be removed from the machine when the user disconnects.

UC-3Select a Component (Essential)

TriggerUser clicks a part in the diagram, or types into a part's search box
PreconditionUC-1 has completed and at least one part is selectable
Basic Path
  1. User clicks a part in the diagram, or types into / clicks that part's search box and clicks a matching result.
  2. The diagram highlights the selected part and the status text updates.
  3. Any previously selected part is cleared.
Alternate Path
  1. The search text matches nothing: the list shows "No matches" and the current selection is unchanged.
PostconditionExactly one part is selected, highlighted, and named in the status line.
RequirementFR-2: Only one component may be selected at a time in the MVP. FR-3: The highlight shall update within one UI frame (≤17 ms) of the click.

UC-4Deselect / Reselect a Component (Essential)

TriggerUser selects a different component while one is already selected
PreconditionA component is currently selected
Basic Path
  1. User selects a new component.
  2. If a test is running, it is stopped (UC-8).
  3. The previous component's highlight and search box are cleared.
  4. The new component is highlighted.
Alternate Path
  1. The user reselects the part that is already selected: nothing changes and any running test continues.
PostconditionOnly the new part is selected and no test is running.
RequirementFR-4: Any running test shall be stopped before the selection changes, so no test is left running against an unselected part.

6. Benchmark Execution

UC-5Run a 2D Workload Benchmark (Essential)

TriggerUser selects the 2D workload and presses Start
PreconditionA component is selected and the 2D workload is valid for it (III.4)
Basic Path
  1. User selects the 2D workload.
  2. User presses Start.
  3. The application launches the real 2D workload on that hardware.
  4. Telemetry polling starts for the target and observed components.
  5. The diagram animates and the readout updates in real time.
Alternate Path
  1. The workload fails to launch: continue at UC-13.
  2. A telemetry read fails during the test: continue at UC-12.
  3. The user presses Stop: continue at UC-8.
PostconditionThe 2D workload is running and live telemetry is shown for the target and observed parts.
RequirementFR-5: The workload shall actually execute on the hardware; no simulated or pre-recorded data shall be shown.

UC-6Run a 3D Workload Benchmark (Essential)

TriggerUser selects the 3D workload and presses Start
PreconditionThe GPU is selected and supports OpenGL 3.3 or later
Basic Path
  1. User selects the 3D workload.
  2. User presses Start.
  3. The application launches a real 3D rendering workload.
  4. Telemetry polling starts for the GPU, plus CPU and RAM as observed parts.
  5. The GPU (and observed parts) animate; the readout shows frame time, utilization, temperature, and power draw.
Alternate Path
  1. The GPU does not support OpenGL 3.3: continue at UC-13.
  2. A component reaches its thermal limit: continue at UC-14.
PostconditionThe 3D workload is running and frame time is shown in the readout.
RequirementFR-6: Frame time shall be shown in the readout for this test, measured by the workload's render loop.

UC-7Run an AI Benchmark Mode Task (Essential)

TriggerUser selects AI Benchmark Mode and presses Start
PreconditionA component is selected, and Ollama is running with the Llama 3.2 3B model installed
Basic Path
  1. User selects AI Benchmark Mode and picks a task goal (e.g., "train a tiny image classifier", "render a scene").
  2. User presses Start.
  3. The application launches the local AI agent inside a sandbox.
  4. The agent plans and carries out the task using only its allowed tools.
  5. Telemetry polling starts for every component the agent's work touches.
  6. The diagram and readout show real, unscripted hardware behavior until the task ends, times out, or the user stops it.
Alternate Path
  1. Ollama is not running or the model is not installed: an error explains how to start Ollama or install the model, and the app returns to the selection state (UC-13).
  2. The task reaches its time limit: the agent is stopped (UC-8) and the summary is marked "time limit reached".
  3. The agent attempts a blocked action (network access, a file outside its folder): the action is refused and logged, and the task continues.
PostconditionThe agent is running inside its sandbox and live telemetry is shown for every part it uses.
RequirementFR-7: The agent's actions shall not be predetermined; hardware behavior is observed, not scripted. FR-8: The agent shall run entirely on the local machine: its model is served by Ollama on localhost, and no request leaves the machine. FR-9: Code the agent runs shall be sandboxed: no administrator rights, no network, file access limited to a dedicated working folder, only approved tools (e.g., run Python in that folder), and a time limit (default 10 minutes).

UC-8Stop a Running Test (Essential)

TriggerUser presses Stop, selects another component, or closes the app
PreconditionA test or AI task is running
Basic Path
  1. The application signals the runner to end the workload.
  2. The workload process ends.
  3. Telemetry polling stops and the diagram returns to idle.
  4. A partial summary is shown, marked "stopped by user".
Alternate Path
  1. The workload does not release the hardware within 2 seconds: its process is force-terminated and the summary notes "force-stopped".
  2. The user closes the app: the test is stopped without a summary and the app exits.
PostconditionNo workload process is running, the diagram is idle, and a partial summary is shown.
RequirementFR-10: A stopped workload shall release the CPU/GPU within 2 seconds; if it does not, its process shall be force-terminated.

UC-9Test Completes (Essential)

TriggerThe workload or AI task finishes on its own
PreconditionA test or AI task was running
Basic Path
  1. The runner reports completion.
  2. Telemetry polling stops.
  3. The diagram returns to idle.
  4. A summary shows duration and the minimum, average, and peak of each metric recorded.
Alternate Path
  1. A metric had no valid samples during the run (e.g., it was unavailable the whole time): the summary shows "no data" for that metric.
PostconditionThe diagram is idle and the summary of the completed run is shown.
RequirementFR-11: The summary shall be computed only from samples actually recorded during the run.

7. Telemetry & Visualization

UC-10Live Diagram Animation from Telemetry (Essential)

TriggerA test or AI task is running
PreconditionTelemetry polling is active for the component(s) involved
Basic Path
  1. Telemetry is polled at 10 Hz or greater.
  2. The diagram updates brightness/motion for the target part based on real utilization.
  3. Observed parts (e.g., RAM feeding the GPU) animate too.
Alternate Path
  1. Telemetry for one part fails: that part follows UC-12 while the others keep animating.
  2. Rendering falls behind: the renderer skips frames rather than delaying telemetry, so latency stays under 200 ms.
PostconditionThe diagram reflects the latest telemetry sample within 200 ms.
RequirementFR-12: Animation shall run at 60 FPS. FR-13: Latency from a hardware sample to its visual reflection shall be under 200 ms. FR-14: Between samples, the animation may interpolate toward the latest sample but shall never display a value outside the range of real samples.

UC-11Live Stat Readout (Essential)

TriggerA test or AI task is running
PreconditionTelemetry polling is active
Basic Path
  1. The application reads the current telemetry values.
  2. The readout shows utilization, memory bandwidth, and temperature at minimum, plus frame time (3D), and power draw / FLOPS when available.
  3. Values refresh on every poll for the duration of the test.
Alternate Path
  1. A metric is not supported on this hardware or needs administrator rights: it shows "unavailable" with the reason.
PostconditionThe readout shows the latest sample for each available metric.
RequirementFR-15: Numbers in the readout shall be the latest raw sample — not cached, averaged, or smoothed. (Smoothing is allowed only in the animation, per FR-14.) FR-16: Every metric shall show its unit and its source (sensor or workload-measured).

8. Error Handling & Safety

UC-12Telemetry Polling Failure (Essential)

TriggerA telemetry source becomes unreadable (sensor failure, permissions issue, unsupported hardware)
PreconditionA test is running or about to run
Basic Path
  1. The application tries to read telemetry for the active component.
  2. The read fails or takes longer than 100 ms.
  3. The application shows a message naming the component and metric that are unavailable.
  4. That part stops animating; its affected numbers show "unavailable".
Alternate Path
  1. The sensor recovers: the part resumes animating and the message clears.
  2. All telemetry for the target part fails: the test is stopped (UC-8), since it can no longer be shown truthfully.
PostconditionThe app is still running; failed metrics show "unavailable" and all other parts keep updating.
RequirementFR-17: A telemetry failure shall not crash the application or affect components still reading correctly.

UC-13Benchmark Fails to Start (Essential)

TriggerUser starts a workload the selected hardware cannot run, or the workload fails to launch
PreconditionA component and workload are selected
Basic Path
  1. User presses Start.
  2. The application detects the combination is unsupported (III.4) or the workload fails to launch.
  3. The application shows an error explaining why and returns to the selection state.
Alternate Path
  1. The user picks a supported workload and presses Start again: continue at UC-5, UC-6, or UC-7.
PostconditionThe app is in the selection state and no workload is running.
RequirementFR-18: No partial or fake telemetry or animation shall be shown after a failed start.

UC-14Thermal Safety Abort (Essential)

TriggerA component's temperature reaches its safety limit during a test
PreconditionA test or AI task is running and temperature telemetry is available
Basic Path
  1. The poller reads a temperature at or above the limit.
  2. The application stops the test (UC-8).
  3. A warning names the component and the temperature reached.
  4. The summary is marked "aborted — thermal limit".
Alternate Path
  1. Temperature telemetry is unavailable at start: the user is warned before the test starts and may continue or cancel.
PostconditionThe test is stopped and a warning names the component and temperature.
RequirementFR-19: Default limits: CPU 95 °C, GPU 90 °C (or the vendor-reported slowdown temperature if lower). The test shall be stopped within 1 second of the limit being read. If temperature is unavailable, the user shall be warned before the test starts.

VI. Appendix — Roadmap

1. MVP Scope — Committed to Build

  • Hardware detection and a diagram of CPU + GPU + RAM as clickable parts
  • Real telemetry for those 3 parts (10 Hz+, under 200 ms latency)
  • Two real workloads: one 2D, one 3D (never simulated), runnable on the local PC or on a rented cloud machine over SSH
  • Diagram animates the active part(s) at 60 FPS from real utilization
  • Live readout per test: utilization, memory bandwidth, temperature (plus frame time for 3D)
  • Stop button, end-of-test summary, and thermal safety abort
  • AI Benchmark Mode: a local, sandboxed AI agent runs an open-ended task while hardware behavior is observed

2. Stretch Goals — If Time Allows

  • Add motherboard/chipset and storage as visualized parts
  • Add a fixed AI/ML workload as a third test type
  • Full AMD and Intel GPU telemetry support
  • Record and replay a test run
  • Compare two runs — or two machines — side by side

3. Ultimate Goal — Beyond Stretch

Run the same piece of software across different hardware — different CPUs, GPUs, machines — and use the visualizer to see how well the code actually uses each one. Where one machine's GPU sits idle while the CPU maxes out, where a routine is serial when the hardware could run it in parallel, where the code itself becomes the bottleneck instead of the hardware — surface those spots directly, instead of just showing a utilization percentage. The goal is finding where code should change to make better use of whatever hardware it's running on, backed by real telemetry from real runs, not static analysis alone.
